Not every job needs an expert

Think about how a help desk works. Easy questions get answered by whoever picks up the phone. Hard ones get passed to a specialist. Nobody sends every question to the most senior person in the building.

AI models work the same way. Small ones are quick and cheap. Large ones cost more and take longer, but they are better at hard problems. Most of the work people send to an AI is easy.

Send everything to the big model

You pay far more than you need to, and everyone waits longer than they should.

Send everything to the small model

People start getting answers that are wrong, and nobody notices for a while.

A model router is the part that picks which one handles each request.

The real question

The question is not "which model is best?"

It is "what is the cheapest option that still gets this right, and how will I know if it didn't?"

What routing is

What model routing means

Choosing which model should handle each request, and deciding before you send it.

A request comes in │ ▼ The router │ ├──▶ Fast model cheap and quick, fine for most work ├──▶ Quality model slower, but thinks things through ├──▶ Premium model for hard problems where mistakes are costly └──▶ HOLD send nothing, because this text should stay private

That last option matters. If the only choices are models, then the program will happily send a private document to a company server without asking. HOLD sends nothing and says why, and the request waits for a person.

People use the word "routing" three ways

Gateway

One doorway into many AI companies, so you only manage one connection. You still choose the model yourself. Examples: OpenRouter, LiteLLM.

Fallback

If one company's service goes down, try another one. This is about staying online, not about picking the best model.

Dynamic ← today

Look at each request and send it to the model that suits it. This is the version that changes what you spend.

All three are useful, and you can use them together. Only the third one changes how much quality you get for your money.

Why not just ask every model?

Send it to all three, compare the answers, keep the best one. It sounds like the version that wins on quality.

So a router has to make a good guess before it spends anything. It never gets to look at the answers first. That one restriction is the whole problem.

If you cut your bill in half but get 8% more wrong answers, you have not saved anything. You have just moved the cost somewhere you are not counting.

Four ways to build a router

ApproachHow it decidesThe catch
By feature Each button in your app uses a fixed model. The summarize button uses the small one, the writing button uses the big one. Too rough. Requests inside one feature still vary a lot.
By written rules ← today You write rules that look for certain words and pick a model based on what they find. The rules pile up and start to conflict. They also cannot improve on their own.
By trained scoring You collect examples of which model did better, then train a small program to score new requests. Based on real data, but it only handles two models well, and you retrain to change anything.
By ranking Rank all your models for each request, the way a streaming service ranks what to show you next. You need a solid testing setup first. In return it handles many models and keeps improving.

We build the second one today because you can read the whole thing in one sitting. The list keeps going after that, and the later options hold up better over time.

A familiar idea

You have seen this before

A request arrives │ ▼ Model router │ ├──▶ Fast model ├──▶ Quality model ├──▶ Premium model └──▶ HOLD (send nothing)

It decides using things like how hard the request is, how risky it is, how much it costs, and how private it is.

Models and harnesses

The model is the head.
The harness is the arms.

A model on its own can think, but it cannot do anything. The harness is all the code around it that lets it act. Every tool or check you add is one more arm, and the head and the arms are both useless without each other. The three yellow arms are the parts we build today.

The order the program checks things

A request arrives │ ▼ 1. Safety rules security, privacy, legal, payments │ └──▶ send to PREMIUM, or hold it back entirely ▼ 2. Simple job rules clearly easy work, or clearly hard work │ └──▶ pick FAST or QUALITY, at no cost ▼ 3. Length check over 1,000 characters │ └──▶ send to QUALITY, still at no cost ▼ 4. The chooser decides a small model, only if no rule matched │ └──▶ picks FAST, QUALITY or PREMIUM, as JSON ▼ 5. Send it to the model │ ▼ 6. Check the answer ├──▶ looks good ──▶ return it to the user └──▶ looks wrong ──▶ try the next model up

This is the router arm from the last slide, opened up. The order is deliberate: the first three steps are free and always behave the same way, so they run before the one that costs money. Notice how little the chooser does. It never solves the problem, and it is never offered HOLD — whether something is too private to send stays a rule a person wrote down.

What does checking an answer mean?

The whole idea rests on catching a bad answer before a person sees it. That sounds hard. Mostly it is not.

The bigger idea

What you actually learned today

You learned how to build something that decides where work should go. Today the choices were AI models, but the program does not really care what the choices are.

Here is the shape of it, and it stays the same no matter what you are sorting:

look at it  # how hard, how risky, how private?
choose      # pick from your list of options
check       # did that actually work?
try again   # if not, use a stronger option
learn       # bad results improve the rules

Any time you have several places work could go, and the work varies in difficulty, this pattern fits. Swap the options and keep the shape. The slides after this one show how bad results feed back in and improve the rules.

Two things to be honest about

Half your users complaining is very late

By the time half your users are unhappy, you have already sent out a lot of bad answers. A number that high only catches a total breakdown. To catch smaller problems you want a much lower limit, plus the idea of sending a small share of traffic to every model and comparing, which finds problems before anyone complains.

Also watch how many requests you are counting. Half of six requests is not a real signal.

"Learning" means two different things

In the program we built today, step 07 is you editing a rule by hand. That is quick and easy to review, but it does not hold up as the system grows.

Once you move up to a trained program, step 07 becomes automatic, and that is when the whole loop can run without a person in it.

That is the real reason to move past word matching. The rules are not wrong. They just cannot learn from step 04 on their own.

What to do next

  • Save every decision. You cannot improve something you are not measuring. Those little cards the program prints are the start of a useful record.
  • Test a small share of traffic. Send about 1 in 100 requests to every model and compare the answers. This is how you find out your rules are wrong.
  • Move past word matching. Once you have that record, a trained program will beat your word list, and you will not have to rewrite it every time a new model comes out.
  • Keep the option to hold things back. That is the one part a better model never replaces.

Send work to the right place.
Check the result.
Try again when it fails.

Small models make everyday work feel fast. Big models protect you when the work is genuinely hard. The router knows which is which, and the check is the part that catches it when the router guesses wrong.
